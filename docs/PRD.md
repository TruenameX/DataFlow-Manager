# DataFlow Manager v0.1 — Product Requirements Document

Статус: требования для согласования и последующей реализации. Язык: русский.
Документ описывает целевую версию v0.1, а не уже реализованные возможности.

## 1. Product Overview

DataFlow Manager — учебное локальное приложение для Data Engineer, предназначенное для централизованного управления конфигурациями источников данных и их последующего использования в ETL-процессах. В v0.1 доступны конфигурации только PostgreSQL и явная проверка подключения к сохранённому источнику через API.

Основание: AGENTS.md, README.md, структура и текущий код репозитория, утверждённые продуктовые решения задачи. Сейчас реализован только FastAPI-маршрут `GET /health` и три теста его HTTP-ответа. В проекте используются Python 3.12, FastAPI, uvicorn, uv и pytest. Служебная БД и управление источниками пока отсутствуют.

## 2. Problem Statement

Data Engineer нужен единый способ сохранять, находить и актуализировать параметры подключения к PostgreSQL, не распространяя пароли в API-ответах и обычных журналах. Перед последующим использованием источника необходимо по запросу проверять доступность подключения с ограничениями времени и сетевого доступа.

v0.1 решает задачу управления конфигурациями. Выполнение ETL остаётся за пределами этой версии.

## 3. Goals & Success Metrics

| Цель | Проверяемый показатель готовности |
|---|---|
| Управлять жизненным циклом конфигурации | Успешно пройдены сценарии создания, списка, чтения, изменения и физического удаления |
| Сохранять конфигурации между запусками | Созданная конфигурация доступна после перезапуска приложения при сохранности служебной БД |
| Защищать учётные данные | Нет открытых паролей в хранилище конфигураций, API-ответах и обычных журналах проверяемых сценариев |
| Выполнять контролируемую проверку подключения | Результат `success` или `failed`; неуспех содержит безопасную категорию; суммарная проверка ограничена 5 секундами |
| Ограничивать сетевую поверхность | Запрещённые фактические адреса не используются; подключения к источникам требуют TLS; API по умолчанию слушает loopback |

Указанные показатели — критерии готовности продукта, а не результаты текущих измерений. Целевые показатели задержки CRUD, нагрузки, объёма конфигураций и методика измерений пока не согласованы (OQ-07). Пользовательские метрики внедрения также не определены.

## 4. Target Users

Основной пользователь — Data Engineer, работающий локально и имеющий параметры PostgreSQL-источника. Он создаёт и поддерживает конфигурации, просматривает их без раскрытия пароля и запускает проверку подключения по необходимости.

Администраторы, роли и многопользовательские права в MVP не моделируются. Локальный режим сам по себе не является механизмом авторизации.

## 5. MVP Scope

### In Scope

- API для создания, списка, просмотра по ID, изменения и физического удаления конфигураций PostgreSQL.
- Хранение конфигураций в служебной PostgreSQL.
- Валидация параметров и уникальность имени без учёта регистра.
- Обратимое шифрование паролей с отдельным от БД ключом.
- Явная проверка только сохранённой конфигурации с таймаутом 5 секунд, без изменения пользовательских данных.
- Allowlist в локальном конфигурационном файле с контролем фактических адресов, включая DNS-разрешение, и обязательный TLS `verify-full` с проверкой доверия сертификату и имени сервера.
- Локальный запуск API с loopback по умолчанию.

### Out of Scope

- Выполнение ETL-пайплайнов.
- Источники CSV и REST API, а также любые типы источников кроме PostgreSQL.
- Расписание задач и Airflow.
- Веб-интерфейс.
- Авторизация и управление ролями.
- Мониторинг качества данных.
- Публичное развёртывание без отдельного проектирования авторизации и безопасности.

В v0.1 история проверок подключения не хранится (OQ-01), пагинация списка отсутствует (OQ-04).

## 6. Data Source Configuration

| Поле | Назначение и ограничения |
|---|---|
| `id` | Стабильный идентификатор записи, назначаемый приложением; формат определится в API-контракте |
| `name` | Имя источника; обязательно, не пустое и уникальное без учёта регистра |
| `host` | Хост PostgreSQL; обязателен, не пустой; фактические адреса подключения должны соответствовать политике allowlist |
| `port` | Обязательный целочисленный TCP-порт в диапазоне 1–65535 |
| `database` | Имя целевой БД; обязательно, не пустое |
| `username` | Имя пользователя PostgreSQL; обязательно, не пустое |
| `password` | Пароль для подключения; передаётся при создании, сохраняется только с обратимым шифрованием и не возвращается API |

В v0.1 тип источника фиксирован как PostgreSQL; дополнительное пользовательское поле типа не требуется. Служебная PostgreSQL хранит конфигурации, а целевая PostgreSQL — пользовательские данные: это разные логические назначения, даже если инфраструктура может совпадать.

Пустой пароль, предельные длины строк, нормализация пробелов и поддерживаемые формы записи хоста требуют уточнения до фиксации схемы валидации. При PATCH отсутствующий `password` сохраняет прежнее значение (закрытый OQ-02); поведение для явно переданных `null` и пустой строки остаётся неутверждённым. TLS `verify-full` утверждён (OQ-08), allowlist хранится в локальном конфигурационном файле (частично закрытый OQ-09). Конфигурация доверия TLS, точная схема allowlist и DNS/IP-механизм ещё требуют уточнения; они не добавляются как произвольно выбранные поля источника.

## 7. Functional Requirements

Идентификаторы FR и AC постоянны: при последующих изменениях не перенумеровываются и не переиспользуются. `AC-XXX.Y` относится к `FR-XXX`. Критерии ниже задают целевое поведение; критерии, зависящие от открытых решений, проверяются после их согласования.

### FR-001 — Создание источника

**Назначение:** сохранить новую конфигурацию PostgreSQL.

**Поведение:** API принимает поля конфигурации, валидирует их и сохраняет запись в служебной PostgreSQL, назначая ID. Создание не запускает проверку подключения.

**Критерии приёмки:**
- **AC-001.1:** при корректных полях и свободном имени создана ровно одна запись с ID; её несекретные поля доступны при чтении по ID.
- **AC-001.2:** при повторном имени операция отклонена без новой записи; параллельные запросы с одинаковым именем не создают дубликаты. Имена, отличающиеся только регистром, считаются одинаковыми (OQ-03).
- **AC-001.3:** создание не обращается к целевому источнику; после перезапуска приложения сохранённая запись доступна.

**Ошибки:** невалидные поля и конфликт имени различимы для клиента; сбой служебной БД не возвращается как успешное создание и не раскрывает секреты.

### FR-002 — Просмотр списка источников

**Назначение:** находить сохранённые источники.

**Поведение:** API возвращает список с ID и несекретными полями конфигураций. В v0.1 пагинация отсутствует (OQ-04).

**Критерии приёмки:**
- **AC-002.1:** список возвращает все сохранённые конфигурации без пагинации и позволяет получить их ID; пароль, его шифротекст и ключ отсутствуют.
- **AC-002.2:** при отсутствии конфигураций возвращается пустой список как успешный результат; чтение списка не проверяет подключения к источникам.

**Ошибки:** недоступность служебной БД возвращается как безопасная ошибка, а не как пустой список.

### FR-003 — Просмотр источника по ID

**Назначение:** получить актуальные параметры выбранной конфигурации.

**Поведение:** API возвращает существующую запись по ID без секретов и без подключения к источнику.

**Критерии приёмки:**
- **AC-003.1:** существующий ID возвращает сохранённые несекретные поля; пароль, шифротекст и ключ отсутствуют.
- **AC-003.2:** неизвестный или удалённый ID возвращает ошибку отсутствия записи без создания новой конфигурации и без сетевой проверки.

**Ошибки:** некорректный формат ID, отсутствие записи и недоступность служебной БД различимы в API-контракте.

### FR-004 — Редактирование источника

**Назначение:** актуализировать параметры существующего источника.

**Поведение:** API валидирует изменения, сохраняет их атомарно и сохраняет ID. Изменения выполняются через PATCH; отсутствующий `password` сохраняет прежнее значение (OQ-02). Уникальность имени проверяется без учёта регистра.

**Критерии приёмки:**
- **AC-004.1:** корректное изменение несекретных полей через PATCH видно при последующем чтении с тем же ID; если `password` не передан, прежний пароль сохраняется; автоматической проверки подключения нет.
- **AC-004.2:** явно переданный допустимый новый пароль заменяет прежний в зашифрованном виде и используется следующей явной проверкой; API не раскрывает ни один пароль.
- **AC-004.3:** невалидное изменение, конфликт имени или неизвестный ID отклонены; при ошибке существующая конфигурация не изменяется частично.

**Ошибки:** ошибка валидации, конфликт имени, отсутствие записи и сбой сохранения сообщаются безопасно. Поведение для явно переданных `null` и пустого пароля остаётся неутверждённым и требует отдельного согласования.

### FR-005 — Физическое удаление источника

**Назначение:** окончательно удалить сохранённую конфигурацию.

**Поведение:** API физически удаляет запись, включая сохранённый шифротекст пароля, из рабочего хранилища конфигураций. Удаление не затрагивает целевую БД.

**Критерии приёмки:**
- **AC-005.1:** после успешного удаления запись отсутствует в служебной таблице, списке и чтении по ID, в том числе после перезапуска; мягкое удаление не применяется.
- **AC-005.2:** удаление неизвестного ID сообщает об отсутствии записи; пользовательские данные целевого источника не изменяются и подключение к нему не выполняется.

**Ошибки:** при недоступности служебной БД успешное удаление не подтверждается. Физическое удаление записи не означает гарантированного стирания резервных копий и журналов самой СУБД.

### FR-006 — Проверка подключения

**Назначение:** по запросу определить возможность подключения к сохранённому PostgreSQL-источнику.

**Поведение:** операция использует актуальную сохранённую конфигурацию, расшифровывает пароль и проверяет подключение с ограничениями FR-009 и FR-010. Она не создаёт и не редактирует конфигурацию; история проверок не хранится (OQ-01). Общий бюджет самой проверки, включая DNS-разрешение, установку соединения и TLS, — не более 5 секунд; это не только таймаут отдельной попытки.

**Критерии приёмки:**
- **AC-006.1:** явный запрос с существующим ID использует сохранённые параметры; успешное подключение возвращает `success`; история проверки не сохраняется ни при успехе, ни при неуспехе.
- **AC-006.2:** неуспешная попытка возвращает `failed` и безопасную категорию ошибки без пароля, строки подключения и сырого сообщения драйвера; перечень категорий ожидает OQ-06.
- **AC-006.3:** при зависшем DNS, установлении соединения, TLS или иной стадии проверка прекращается в пределах общего бюджета 5 секунд, возвращает `failed` с безопасной категорией и освобождает открытые ресурсы.
- **AC-006.4:** в целевой БД не выполняются операции изменения пользовательских данных или схемы; открытые соединения закрываются после завершения проверки.
- **AC-006.5:** неизвестный ID или непереданная сохранённая конфигурация не запускают сетевую попытку; передача произвольных параметров вместо сохранённого источника не поддерживается.

**Ошибки:** отсутствие записи, неверный запрос и невозможность получить конфигурацию из служебной БД — ошибки операции API. Отрицательный результат самой проверки — `failed`; точные HTTP-коды и схема ответа определяются в API-контракте.

### FR-007 — Валидация конфигурации

**Назначение:** исключить сохранение некорректных параметров.

**Поведение:** при создании и изменении проверяются обязательность, типы, непустые значения полей согласно разделу 6, диапазон порта и уникальность имени без учёта регистра. Валидация не является проверкой доступности источника.

**Критерии приёмки:**
- **AC-007.1:** отсутствие обязательного поля при создании, пустые обязательные несекретные строки, нецелый порт или порт вне 1–65535 отклоняются с указанием проблемного поля без раскрытия пароля.
- **AC-007.2:** правила валидации одинаковы для создаваемых и изменяемых значений; отклонённый запрос не сохраняет частичные изменения и не запускает проверку подключения.

**Ошибки:** ответ описывает нарушение безопасно и не повторяет входной пароль. Неопределённые правила из раздела 6 требуют уточнения до реализации соответствующих проверок.

### FR-008 — Защита учётных данных

**Назначение:** сохранять возможность подключения без раскрытия паролей.

**Поведение:** пароль хранится с обратимым шифрованием; ключ находится отдельно от служебной БД и не попадает в Git. Хеширование вместо шифрования не удовлетворяет требованию подключения. Конкретный алгоритм и способ передачи ключа выбираются при техническом проектировании.

**Критерии приёмки:**
- **AC-008.1:** сохранённое значение пароля является шифротекстом; при корректном внешнем ключе приложение может использовать исходный пароль для проверки подключения.
- **AC-008.2:** ключ отсутствует в служебной БД и отслеживаемых Git-файлах; без доступного корректного ключа операции, требующие шифрования или расшифрования, завершаются безопасной ошибкой без перехода к хранению открытого пароля.
- **AC-008.3:** ответы всех операций, ошибки валидации и обычные журналы, включая ошибки драйвера, не содержат пароль; API также не возвращает шифротекст и ключ.

**Ошибки:** сбой шифрования, расшифрования или доступа к ключу не раскрывает секреты и не приводит к частичному сохранению конфигурации.

### FR-009 — Ограничение сетевых подключений

**Назначение:** ограничить проверку заранее разрешёнными хостами и адресами.

**Поведение:** перед сетевой попыткой применяется allowlist; проверяется не только строка `host`, но и фактические адреса подключения после DNS-разрешения. Подключение к адресу, не разрешённому политикой, запрещено. Allowlist хранится в локальном конфигурационном файле; точная схема, правила управления и DNS/IP-механизм остаются открытыми в OQ-09.

**Критерии приёмки:**
- **AC-009.1:** запрос проверки запрещённого хоста завершается `failed` с безопасной категорией без попытки соединения с запрещённым адресом.
- **AC-009.2:** разрешённое имя, разрешившееся в запрещённый адрес, не позволяет подключиться к этому адресу; для IP-литерала также применяется проверка разрешения.
- **AC-009.3:** при нескольких DNS-адресах, повторном разрешении или смене адреса между проверкой и соединением ни одна попытка, включая резервные, не использует непроверенный или запрещённый фактический адрес.
- **AC-009.4:** отсутствие применимой разрешающей политики или невозможность подтвердить разрешённость адреса не разрешают подключение по умолчанию.

**Ошибки:** отказ политики и ошибки разрешения адресов возвращаются безопасно; точные категории зависят от OQ-06. Окончательная матрица разрешённых случаев зависит от OQ-09.

### FR-010 — TLS-подключение

**Назначение:** обеспечить шифрование соединения с целевым PostgreSQL и проверку подлинности сервера.

**Поведение:** проверка подключения обязательно использует TLS `verify-full` с проверкой доверия сертификату и имени сервера (OQ-08). Откат к открытому соединению или режиму без этих проверок не допускается.

**Критерии приёмки:**
- **AC-010.1:** `success` возможен только при установленном TLS-соединении в режиме `verify-full`, прошедшем проверку доверия сертификату и имени сервера; сервер без поддержки TLS приводит к `failed` без повторной попытки открытого соединения.
- **AC-010.2:** сбой TLS, недоверенный или просроченный сертификат, а также несовпадение имени сервера возвращают `failed` с безопасной категорией без раскрытия секретов и без отката к менее строгому режиму.

**Ошибки:** ошибки TLS не обходятся отключением шифрования, проверки доверия сертификату или имени сервера. Способ настройки доверенных CA и их обновления ещё требует технического согласования; выполнение требования должно быть подтверждено тестами.

### FR-011 — Локальный режим приложения

**Назначение:** ограничить доступ к API локальной машиной по умолчанию.

**Поведение:** стандартный запуск использует loopback-интерфейс. Публичное развёртывание без отдельного проектирования авторизации и безопасности не поддерживается.

**Критерии приёмки:**
- **AC-011.1:** при запуске по документированной команде API доступен через loopback и не слушает внешние интерфейсы; адреса `0.0.0.0` и `::` не используются по умолчанию.
- **AC-011.2:** эксплуатационная документация обозначает локальный режим и запрет публичного развёртывания без дополнительного проектирования безопасности; авторизация и роли не заявлены как реализованные в MVP.

**Ошибки:** невозможность занять локальный адрес или порт должна быть диагностируема без раскрытия секретов. Дополнительная защита локального API остаётся OQ-05.

## 10. Non-Functional Requirements

- **NFR-001 — Сохранность:** подтверждённые изменения переживают перезапуск приложения; неуспешная запись не оставляет частичного состояния. Недоступность служебной БД не маскируется успехом.
- **NFR-002 — Конфиденциальность:** секреты защищены согласно FR-008 на успешных и ошибочных путях, включая сообщения зависимостей.
- **NFR-003 — Сетевые ограничения:** каждая проверка подчиняется allowlist из локального конфигурационного файла, TLS `verify-full` с проверкой доверия сертификату и имени сервера и общему таймауту 5 секунд; ресурсы соединения освобождаются.
- **NFR-004 — Производительность:** таймаут проверки утверждён; остальные показатели и метод измерения ожидают OQ-07. Конкретные RPS, объёмы и задержки не обещаются.
- **NFR-005 — Сопровождаемость:** бизнес-логика отделена от API-маршрутов; решения простые и проверяемые, в соответствии с AGENTS.md.
- **NFR-006 — Совместимость:** целевой стек — Python 3.12, FastAPI, PostgreSQL, pytest и uv. Новые библиотеки потребуют обоснования на этапе реализации.
- **NFR-007 — Диагностируемость:** ошибки доступны для диагностики без секретов; точный каталог категорий и API-формат должны быть согласованы. Наблюдаемость не расширяется до мониторинга качества данных.

## 11. Dependencies & Assumptions

- Для целевой реализации необходима доступная служебная PostgreSQL. В текущем репозитории её нет; PRD фиксирует потребность, но не добавляет БД, Docker, зависимости или код.
- Параметры служебной БД, управление схемой и способ предоставления ключа определяются техническим проектированием. Служебные секреты также не должны попадать в Git и обычные журналы.
- Для успешной проверки нужны доступный PostgreSQL-источник, TLS, разрешённые сетевые адреса и корректные учётные данные.
- Для безопасной реализации необходимы технические решения по настройке доверенных CA, точной схеме локального файла allowlist и DNS/IP-механизму. TLS `verify-full` и локальное хранение allowlist уже утверждены; открытые детали реализации не отменяют эти ограничения.
- REST-маршруты и HTTP-методы согласованы: `POST /api/v1/sources` — создание, `GET /api/v1/sources` — список, `GET /api/v1/sources/{id}` — просмотр, `PATCH /api/v1/sources/{id}` — редактирование, `DELETE /api/v1/sources/{id}` — удаление, `POST /api/v1/sources/{id}/check` — проверка подключения. HTTP-коды, JSON-схемы запросов и ответов (включая ошибки) и формат ID пока являются проектными предложениями и требуют согласования.
- v0.1 предназначена для доверенной локальной среды с тестовыми учётными данными. Loopback не заменяет авторизацию. Дополнительная защита от других локальных процессов и пользователей требует отдельного решения (OQ-05).
- Широкое назначение управления ETL в README и формулировка «PostgreSQL (later)» в AGENTS.md относятся к контексту развития проекта. Для v0.1 границы определены этим PRD: конфигурации PostgreSQL без выполнения ETL.

## 13. Definition of Done

Следующие условия относятся к готовности **реализации v0.1**, а не к выполнению задачи написания PRD:

- Реализованы все 11 FR; проверены все 30 AC с зафиксированными результатами.
- Согласованы влияющие на реализацию открытые вопросы и уточнения; для исключённых из версии возможностей явно зафиксирована граница. Неопределённые сценарии не объявлены прошедшими приёмку.
- Зафиксирован API-контракт, согласованный с требованиями, включая безопасные ошибки и поведение обновления пароля.
- Проверены CRUD, сохранность после перезапуска, конкурентная уникальность и отсутствие частичных изменений.
- Проверены шифрование, внешний ключ и отсутствие секретов в ответах и обычных журналах.
- Проверены общий таймаут, отсутствие изменений целевых данных, TLS `verify-full` с проверкой доверия сертификату и имени сервера без отката и запрет подключения к неразрешённым фактическим адресам, включая DNS-сценарии.
- Подтверждён loopback по умолчанию; документированы запуск, служебная БД, настройка ключа, сетевой политики и ограничения публичного развёртывания.
- Добавлены и реально выполнены релевантные тесты нового поведения; существующие тесты `/health` проходят. `/health` сохраняет ответ HTTP 200, JSON `{"status": "ok"}`, `application/json` и независимость от БД и внешних сервисов согласно README.
- Изменения не добавляют исключённые функции MVP; новые зависимости обоснованы, бизнес-логика отделена от маршрутов.

Для текущей задачи готовность означает создание только `docs/PRD.md`, проверку его структуры, идентификаторов, полноты и непротиворечивости. Реализация приложения и подтверждение прохождения продуктовых критериев в эту задачу не входят.
