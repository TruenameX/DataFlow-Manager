# TASK-005 — процедура integration (не исполнялась)

## Границы и разрешения

Реальный сервер, его владелец, роли, credentials и инвентарь TASK-004 не
подтверждены. До выполнения подготовить и согласовать: подтверждение владельца
и изоляции loopback-стенда; полный инвентарь TASK-004; имена новой БД и ролей;
отдельные разрешения на обследование, создание ресурсов, подключения, SQL,
миграции и тесты. Cleanup требует отдельного последующего разрешения.
Присутствие флагов допуска не доказывает ни разрешения, ни изоляции.

## Идентификаторы и реестр

Для каждого запуска сгенерировать новый UUIDv4 и передать его в
`plan_resources` вместе с проверенным непустым инвентарём защищаемых ресурсов.
Он возвращает имена `task005_<uuidhex>`, `task005_prep_<uuidhex>` и
`task005_test_<uuidhex>`. Сверить имена с инвентарём и, после разрешённого
подключения, с фактическим сервером; совпадение — остановка. Имена не являются
доказательством принадлежности. Вести реестр фактически созданных ресурсов,
времени и операций без паролей, DSN, raw exception и значений окружения.

## Параметры и подготовка после разрешения

Test Profile v1.0: PostgreSQL 18.6, `127.0.0.1:5432`, отдельные preparation и
test роли; pool 2+1, timeout 5, connect timeout 3, pre-ping true, recycle 1800,
READ COMMITTED, echo false, hide_parameters true. Принятая фабрика принудительно
задаёт sslmode=disable, gssencmode=disable и require_auth=scram-sha-256;
применять только на подтверждённом изолированном loopback-стенде.

После отдельного разрешения оператор проверяет владельца/изоляцию сервера,
инвентарь TASK-004, версию и настройки pg_hba. Создать только согласованные
базу и две роли, запретить test-роли создание БД/ролей и выдачу прав. Выдать
test-роли CONNECT к новой БД, USAGE на согласованную тестовую схему и только
необходимые SELECT/INSERT на `task005_probe`; проверять эффективные права.
Пароли вводить через согласованный защищённый интерактивный канал, не в SQL,
командную строку, журнал или файл репозитория.

Параметризованная последовательность ниже — проект для отдельного утверждения,
не проверенные команды. Подставлять только идентификаторы из сверенного реестра;
`<ADMIN_ROLE>` и права на подключение должны быть подтверждены владельцем.
Запустить `psql` вручную после разрешения (пароль запрашивается `-W`):

```text
psql -X -W -v ON_ERROR_STOP=1 -h 127.0.0.1 -p 5432 -U <ADMIN_ROLE> -d postgres
```

Внутри сессии сначала проверить `SELECT current_user, current_database(),
version(), inet_server_addr(), inet_server_port();` и сверить с утверждённым
стендом. Только после проверки и разрешения на SQL задать безопасно проверенные
идентификаторы через `\set db 'task005_<uuidhex>'`,
`\set prep 'task005_prep_<uuidhex>'`, `\set test 'task005_test_<uuidhex>'` и
выполнить следующие команды в psql (идентификаторы экранируются синтаксисом
`:\"name\"`; CREATE DATABASE выполняется вне транзакционного блока):

```sql
CREATE ROLE :"prep" LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION;
CREATE ROLE :"test" LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION;
CREATE DATABASE :"db" OWNER :"prep";
REVOKE CONNECT ON DATABASE :"db" FROM PUBLIC;
GRANT CONNECT ON DATABASE :"db" TO :"test";
```

Использовать интерактивные `\password` для обеих ролей только после согласования
секретного канала и включения на стенде SCRAM. После разрешения подключиться как
preparation-role к новой БД, проверить `SELECT current_database(), current_user;`,
затем создать таблицу указанной ниже командой и выдать test-role:

```sql
GRANT USAGE ON SCHEMA public TO :"test";
GRANT SELECT, INSERT ON TABLE public.task005_probe TO :"test";
```

Проверить через авторизованные `SELECT` системных каталогов отсутствие superuser,
CREATEDB, CREATEROLE, REPLICATION и членства в привилегированных ролях, а также
эффективные CONNECT/USAGE/SELECT/INSERT. Точную проверку членства и pg_hba
утвердить с владельцем стенда до выполнения. Зафиксировать каждую успешную
операцию в реестре; недостоверный результат — остановка, не автоматический retry.

В новой БД после отдельного разрешения preparation-role создаёт тестовую таблицу:

```sql
CREATE TABLE task005_probe (probe_id text PRIMARY KEY, value text NOT NULL);
```

Тесты записывают UUID-ключи; commit-проверки оставляют строки в этой таблице.
Записать таблицу и результаты в реестр. Никаких автоматических DELETE/DROP.
Если нужны миграции приложения, требуется отдельное разрешение: `migrations/env.py`
принимает только явно переданное connection; обычный Alembic CLI без такого
connection не является подготовленной командой онлайн-миграции. Не запускать
миграции до подготовки и отдельного review авторизованного вызывающего кода.

## Допуск и запуск после разрешения

Передать все обязательные DFM_DB_* через согласованный защищённый канал; никакие
PG*-переменные, включая пустые, не допускаются. Оператор задаёт отдельно:
`DFM_TEST_INTEGRATION=YES`, `DFM_TEST_OWNER_APPROVED=YES`,
`DFM_TEST_ISOLATED_SERVER=YES`, `DFM_TEST_SQL_APPROVED=YES`,
`DFM_TEST_INVENTORY_VERIFIED=YES`, `DFM_TEST_APPROVED_DATABASE=<точная_база>`,
`DFM_TEST_PREPARATION_ROLE=<точная_роль>` и непустой разделённый запятыми
`DFM_TEST_EXCLUDED_RESOURCES=<проверенный_инвентарь_TASK004>`. Это утверждения
оператора, а не криптографическое или серверное доказательство.

До физического подключения fixture проверяет эти утверждения, принятый M1 и
профиль. После разрешённого подключения первым явным SQL fixture проверяет current_database,
current_user, server_version_num, адрес и порт. Несовпадение — отказ до SQL
сценариев. До этого драйвер и dialect могут выполнять инициализирующие SQL;
они тоже требуют отдельного разрешения. Первое подключение предшествует проверке
серверной identity; локальный адрес и имя не доказывают владельца или изоляцию.
Эти проверки не доказывают владельца сервера или фактические права.
Затем, после отдельного разрешения на integration-тесты:

```text
.venv/bin/python -B -m pytest -p no:cacheprovider tests/integration/test_task005_pending.py
```

Последовательность приёмки: d1 (процедура/fixtures), d2 (ресурсы и реестр),
e1 (commit/rollback/изоляция), e2 (auth, pool и освобождение). Тесты также
проверяют версию, роль, capability, отрицательный пароль и health. Фактический
server-side fallback, права, pg_hba, pre-ping при сетевом disconnect и физическое
освобождение требуют отдельного проверяемого плана; текущий код не доказывает
все эти условия. Не показывать реальные credentials в отчёте или output.

## Остановка и очистка

При несовпадении инвентаря, роли, адреса, версии, auth или прав остановиться до
дальнейших операций. При ошибке не повторять автоматически и не выбирать другой
сервер. Для cleanup сначала представить фактический реестр созданной таблицы,
базы и ролей; получить отдельное разрешение на конкретные команды. Ни удаление
ресурсов, ни уничтожение строк не включены в разрешение на подготовку/тесты.
